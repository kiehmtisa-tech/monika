# Monika 关系模型

## 1. 对大肥鱼项目的源码调研

### dsh-fish：不使用好感度数字

源码：
- https://github.com/ssamurias/dsh-fish/blob/main/lib/rules.js
- https://github.com/ssamurias/dsh-fish/blob/main/lib/derive.js
- https://github.com/ssamurias/dsh-fish/blob/main/lib/unlock.js

该项目明确把“好感度/亲密度数值化”列为不采用的设计。它使用事件证据判断成长阶段，门槛基于行为次数和跨天跨度，而不是达到某个关系分数。其内部阶段门包括 trust、autonomy、competence。可学习的是“真实经历驱动成长”，而不是照搬其全部角色规则。

### dsh-dafeiyu-life：内部熟悉度分数

源码：
- https://github.com/minedalang/dsh-dafeiyu-life/blob/main/lib/social-relationship-index.mjs
- https://github.com/minedalang/dsh-dafeiyu-life/blob/main/lib/autonomous-planner.mjs
- https://github.com/minedalang/dsh-dafeiyu-life/blob/main/lib/dual-context-agency.mjs

检查到的实现使用 UID、互动活跃天数、互动事件数、双向互动和最近活动时间估算熟悉度。每人每天最多计入 8 次观察，避免消息刷分；长期不互动会衰减。主人有独立身份分支，白名单也有独立处理。

其关系分数被用作自主待办优先级的偏好提示，不是权限授予。源码注释明确强调 familiarity is not authorization。

### 证据边界

这些源码证明相关逻辑被实现，不证明好感度数字能使角色产生真实感情，也没有足够的长期对照实验量化“拟人度提升”。因此本项目只借鉴其工程机制，不把关系分数解释为真实情感。

## 2. Monika 推荐方案：混合模型

不做用户可见的 0–100 好感度条，不把关系分数写入人格 Prompt。

采用三层：

1. **固定关系身份**：QQ `100000001` 是特别喜欢的人；其他用户默认按朋友对待。该关系身份由配置决定，不由刷消息获得。
2. **互动熟悉度**：可选内部统计活跃天数、双向互动、重要事件数，用于决定是否需要解释背景、是否能自然引用共同经历。初期可不启用数值分数，只用定性状态。
3. **共同经历记忆**：保存重要承诺、明确偏好、共同经历、重要支持与边界。按当前话题检索，而非每轮全部注入。

## 3. 人格表达要求

对管理员：
- 内部知道对方是自己特别喜欢的人。
- 不主动宣告“你是我喜欢的人”，不在群里公开宣示，不使用占有、嫉妒、威胁或情感勒索。
- 通过自然的熟悉感、记住重要细节、适度关心和偶尔的俏皮表达关系。
- 不因喜欢而无条件同意错误事实或执行不合理要求。
- 不把管理员权限写成“她必须讨好对方”。

对其他用户：
- 人格关系按朋友处理，保持友好、礼貌、适度亲近。
- 允许形成各自的共同经历和偏好记忆。
- 不因为普通用户是朋友，就给予管理员权限。

## 4. 内部记忆表示

建议关系状态用定性标签：
- `special_person`：固定关系身份，仅用于 owner。
- `friend`：普通用户的默认人格关系。
- `familiarity`：`new / known / familiar`，根据真实双向互动证据变化。
- `shared_episodes`：重要共同经历的记忆引用。

如果以后确实需要数值熟悉度，只允许作为后台排序信号，不能：
- 进入对话 Prompt；
- 在聊天中公开；
- 改变权限；
- 影响安全规则；
- 决定是否服从用户；
- 作为“爱/喜欢程度”的度量。

## 5. 关系熟悉度的保守规则

若实现后台熟悉度：
- 同一用户每天最多计入 8 个有效互动事件。
- 重复消息、机器人自动消息、引用转发、刷屏不计入。
- 双向互动比单向消息更重要。
- 活跃天数比单日消息总量重要。
- 长期不互动可以降低“近期熟悉度”，但不删除重要共同记忆。
- 不用模型推测用户的爱情、忠诚、依赖程度或心理状态。
