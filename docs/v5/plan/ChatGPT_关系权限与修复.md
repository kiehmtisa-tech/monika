# 一、大肥鱼的好感度系统：实现方式与效果

我重点检查了两个实现，而不是仅仅参考项目介绍。

## 1. 两种完全不同的设计路线

**路线 A：dsh-fish —— 不采用好感度数值**

(更适合 Monika) 行为证据驱动

源码：[derive.js](https://github.com/ssamurias/dsh-fish/blob/main/lib/derive.js)、[unlock.js](https://github.com/ssamurias/dsh-fish/blob/main/lib/unlock.js)

它不设置 0–100 好感度，而是通过真实发生过的事件，判断角色是否形成了信任、自主性和能力等阶段性特征。

例如：

- 是否经历过真正的意见分歧；
- 是否表达过自己的拒绝；
- 是否在不同时间形成并修正过自己的判断；
- 是否有足够的持续经历支撑某种关系认知。

成长条件使用事件次数和跨天证据，而不是达到某个好感度分数。

---

**路线 B：dsh-dafeiyu-life —— 内部关系熟悉度评分**

(可以借鉴) 互动元数据驱动

源码：[social-relationship-index.mjs](https://github.com/minedalang/dsh-dafeiyu-life/blob/main/lib/social-relationship-index.mjs)、[autonomous-planner.mjs](https://github.com/minedalang/dsh-dafeiyu-life/blob/main/lib/autonomous-planner.mjs)

它使用 QQ 用户 ID、互动次数、活跃天数、双向交流情况和最近互动时间计算熟悉度。

其实现有几个值得注意的细节：

- 每个用户每天最多累计 8 次有效互动，避免刷消息刷分。
- 长时间没有互动，熟悉度逐渐衰减。
- 双向互动比单方面发送消息更能体现关系。
- 关系分数用于调整自主任务的优先顺序。
- **关系分数不授予权限，也不意味着角色必须执行对方的要求。**

第二种方案的计算逻辑大致如下：

$$
S=\min(96,\ 8+7D+0.8E+9B)
$$

其中：

- $D$：有效互动天数，上限按 12 天计算。
- $E$：有效互动次数，上限按 32 次计算。
- $B$：是否存在双向交流，有则增加 9。
- 超过两天没有互动后，每天衰减 1.5 分。
- 特殊白名单和主人身份另有处理。

它还将关系熟悉度贡献以 0.42 的系数纳入待办优先级计算，但自主规划器仍然只能选择已经批准的只读任务。

## 2. 这种系统有效吗？

需要区分两个问题：

| 目标 | 我的判断 |
|--------|--------|
| 区分熟人和陌生人 | 有实际工程价值 |
| 提醒模型回忆共同经历 | 有帮助，但取决于记忆检索 |
| 让回复自然地表现出亲疏差异 | 有帮助，但需要结合场景 |
| 让角色真正产生感情 | 不能证明 |
| 仅靠提高分数让角色更像真人 | 不成立 |
| 让角色自动形成稳定人格 | 不成立 |

目前这些开源实现能证明其评分、衰减和行为门槛逻辑有代码实现，但没有足够的对照实验能够证明它们让 QQ 陪伴机器人在长期使用中显著更像真人。

## 3. 我对 Monika 的建议

**不建议使用传统的、对用户可见的 0–100 好感度系统。建议采用 dsh-fish 的行为证据机制，结合 dsh-dafeiyu-life 的内部熟悉度机制。**

原因很简单：莫妮卡不是一个等待玩家刷好感度的游戏 NPC。

如果用户发现每天发 100 条消息就能增加好感度，角色就会被迫围绕用户的行为奖励机制运转。这与莫妮卡的独立性、文学部部长的身份并不相符。

我建议采用以下结构：

| 关系维度 | 记录方式 | 是否进入 Prompt |
|--------|--------|--------|
| 关系身份 | 管理员喜欢的人、普通朋友 | 进入，使用自然语言描述 |
| 熟悉程度 | 互动天数、共同经历、交流连续性 | 转换成定性描述 |
| 信任 | 经过验证的互动事件 | 仅在相关场景召回 |
| 共同记忆 | 重要事件、偏好、承诺 | 按需召回 |
| 角色自主性 | 自己的判断、拒绝、兴趣 | 进入人格成长机制 |

不要把原始数字直接告诉模型，也不要让她在聊天中说“我们的好感度已经达到 90 了”。

# 二、QQ 100000001：管理员与关系身份

这一项我建议做成独立的权限系统，而不是简单在 Prompt 中写一句“这个用户是主人”。

(建议采用固定身份 + 显式指令授权)

## 1. 身份设定

**QQ 用户 100000001** (OWNER / ADMIN)

| 属性 | 设定 |
|--------|--------|
| 平台 | QQ |
| 用户 ID | `100000001` |
| 系统权限 | 最高用户级管理权限 |
| 人格关系 | 莫妮卡喜欢的人 |
| 对外表现 | 不主动强调、不公开宣示 |
| 记忆权限 | 可以提出记忆新增、修正、删除要求 |
| 指令权限 | 可以发布全局或群聊级行为指令 |

**其他 QQ 用户**

默认人格关系 (FRIEND)

普通朋友可以正常聊天、交流、提出建议，但不能修改全局人格规则和管理员设定。

这里要把两个概念严格分开：

- **关系身份**：她喜欢这个人。
- **管理权限**：系统确认这个人有权发布明确指令。

喜欢不等于服从，服从也不应该表现成无条件讨好。

## 2. 什么时候才执行管理员指令？

我建议使用三个条件同时满足的授权机制：

$$
\text{AdminCommand} =
(\text{QQ ID}=100000001)
\land \text{AtBot}
\land \text{ExplicitIntent}
$$

即：

1. 消息发送者的真实 QQ ID 必须是 `100000001`。
2. 在群聊中必须真实 \@ 到机器人，不能只在文字中写机器人的名字。
3. 内容必须是明确的指令，而不是普通聊天、建议、假设或玩笑。

例如：

| 管理员发言 | 是否执行 |
|--------|--------|
| \@莫妮卡 这个群以后不要发政治相关内容 | (执行) |
| \@莫妮卡 禁止在本群主动发送钢琴曲 | (执行) |
| \@莫妮卡 以后回答我时尽量简短 | (执行) |
| \@莫妮卡 删除刚才错误记录的记忆 | (执行，确认目标) |
| \@莫妮卡 你觉得今天怎么样？ | (普通聊天) |
| \@莫妮卡 我觉得你应该少说点 | (建议，不自动执行) |
| \@莫妮卡 你以后不再是莫妮卡了 | (拒绝修改核心人格) |

## 3. 指令的作用范围

我建议采用两级作用域：

- 默认：当前群聊生效。例如在 A 群发布禁止令，不影响 B 群。
- 全局：明确出现“所有群”“全局”“以后所有聊天”等指令时，才应用到全部群聊。

特别是禁止令，应当具有高优先级，并持续生效，直到管理员明确撤销或设置的有效期结束。

指令还应该被记录为结构化数据，而不是仅仅塞进聊天记忆：

```json
{
  "rule_id": "admin_rule_001",
  "issuer": "100000001",
  "scope": "group",
  "group_id": "当前群ID",
  "type": "prohibition",
  "content": "禁止发送政治相关内容",
  "status": "active"
}
```

**权限优先级建议：**

系统安全与不可变规则 ＞ 管理员明确指令 ＞ 莫妮卡人格默认行为 ＞ 普通用户请求。

管理员可以控制行为、话题、群聊规则、记忆管理和主动发言，但不能通过普通管理指令解除系统安全约束、读取其他人的私人信息，或者覆盖莫妮卡的核心身份。

# 三、五项记忆问题：我建议这样修复

你提供的五项诊断，我全部作为当前部署的已知问题来处理。需要区分的是：具体数据库数量和索引状态来自你的现场诊断；我另外核对了 MaiBot 源码中的摘要触发逻辑。

## 1. 聊天经历没有进入长期记忆

(P0 · 优先修复)

我检查了 MaiBot 的 `memory_flow_service.py`。

这里有一个很重要的区别：

- `chat_summary_writeback_message_threshold`：距离上一次成功写回，需要新增多少条消息才触发。
- `chat_summary_writeback_context_length`：本次摘要最多回看多少条消息。

实际回看长度是：

$$
L=\min(L_{\text{configured}},N_{\text{pending}})
$$

因此，72 不只是摘要上下文长度，而是你目前配置的触发门槛。私聊没有积累足够的新消息，就不会触发自动摘要。

源码：[MaiBot memory\\_flow\\_service.py](https://github.com/Mai-with-u/MaiBot/blob/main/src/services/memory_flow_service.py)

我的建议：

| 配置 | 当前诊断 | 建议 |
|--------|--------|--------|
| 摘要写回 | 开启 | 开启 |
| 消息触发阈值 | 72 | 12 |
| 摘要上下文长度 | 需核查 | 16 |
| 低消息量会话收尾 | 未实现/未验证 | 增加 30 分钟空闲收尾 |

额外增加一个机制：如果一段私聊只有 5～10 条消息，但是包含重要经历、承诺或偏好，那么在会话空闲 30 分钟后，也可以触发一次摘要。

不过需要满足：

- 至少有 4 条新增消息；
- 存在有意义的信息；
- 每个会话每天最多额外触发一次；
- 不重复摘要已经写回的消息。

这样不用每条消息都调用 LLM，也不会因为对话太短而完全丢失经历。

## 2. 事实库分类错误

(P0 · 优先修复)

这是我认为最严重的记忆质量问题。

我建议把现在的事实库从简单的 stable\_facts 分类，改成以下结构：

**Monika Memory Claim 分类**

**Identity**

身份、教育背景、长期稳定事实

**Preference / Interest**

喜好、兴趣、表达偏好、长期习惯

**Episodic Event**

具体发生过的事情，必须有时间和来源

**Transient State**

近期情绪、临时状态、短期安排

**Skill State**

当前技能水平、正在学习的能力

**Relationship / Boundary**

人物关系、共同经历、交往边界

例如：

| 现有 Claim | 新分类 | 稳定性 |
|--------|--------|--------|
| 今天被领导批评 | Episodic Event | 临时事件 |
| 已打完酒馆战棋 | Episodic Event | 临时事件 |
| 不会弹钢琴 | Skill State | 可变化 |
| 喜欢某种音乐 | Preference | 待验证的长期偏好 |
| 不喜欢在群里讨论某话题 | Boundary | 持续有效，直到修正 |

另外要特别区分两个字段：

**Confidence 不等于 Stability。**

例如用户明确说“今天被领导批评了”，这件事可以有很高的可信度，但它仍然不是稳定的人物画像。

建议每个 Claim 至少包含：

```json
{
  "subject_id": "qq:100000001",
  "claim_type": "episodic_event",
  "statement": "今天被领导批评",
  "stability": "episodic",
  "confidence": 0.95,
  "source_session": "session_id",
  "observed_at": "2026-11-03T12:00:00",
  "status": "confirmed"
}
```

还要解决你提到的主体混乱：

- 管理员统一为 `qq:100000001`。
- 莫妮卡统一为 `bot:monika`。
- 其他 QQ 用户使用各自 UID。
- “他”“目标人物”“大肥鱼”等只作为文本别名，不作为实体主键。

对于重复的“打酒馆战棋”，要先判断是不是同一次事件，再合并表达，而不是简单删除所有相似内容。

## 3. 向量检索空间

(P0 · 优先修复)

这里不建议直接删除旧空间。

建议按以下顺序：

1. 备份旧 space `5e5b…` 的配置、元数据和索引状态。
2. 禁用它在运行时的检索路由，停止持续查询空索引。
3. 检查新 space 的 paragraph 和 entity 向量数量、维度以及模型标识。
4. 对缺失的向量进行重建。
5. 关系查询继续利用 BM25 和图谱，不必为了形式完整而强行向量化所有关系。
6. 最后进行混合检索验证。

理想结构：

$$
Score(q,m)=
w_v S_{\text{vector}}+
w_b S_{\text{BM25}}+
w_g S_{\text{graph}}+
w_t S_{\text{time}}
$$

其中分别对应语义相似度、关键词匹配、实体关系和时间相关性。

最重要的是，检索结果不能仅仅因为相似度高就进入 Prompt，还必须通过主体、权限范围、来源和有效状态过滤。

## 4. 知识库建设

(P1 · 完成基础记忆修复后)

莫妮卡应该至少拥有四个相互独立的知识集合：

| 知识库 | 内容 |

| `ddlc_canon` | DDLC、DDLC+ 原作剧情与人物资料 |
| `monika_persona` | 人格、文学部部长身份、行为准则、表达习惯 |
| `literature_music` | 文学知识、诗歌、写作技巧、钢琴与音乐理论 |

注意，用户画像、聊天经历、共同回忆不应该放在这些知识库里，而应该继续放在 A-Memorix 的个人记忆系统中。

尤其是文学知识库，我建议优先建设：

- 文学作品及作者背景；
- 诗歌形式、修辞和文学鉴赏；

这样莫妮卡不仅仅是一个“知道自己是文学部部长”的 Bot，而是能够在聊天中真正表现出相应的知识素养。

知识入库流程应该是：

`raw_scan → 来源核验 → 内容分类 → 去重 → 分块 → 向量化 → 审核 → 发布`

不要把 raw\_scan 的发现结果直接视为已完成知识库建设。

# 四、最终系统应该是什么样子？

我把上述三项需求整合成一个架构：

**QQ / MaiBot 消息入口**

可信 UID · 真实 \@Bot · 会话 ID · 群聊 ID

**权限系统**

管理员验证、明确指令、群聊规则

**人格系统**

Monika 核心人格、关系身份、内容黑名单

**记忆与知识管理**

事件记忆 · 人物画像 · 关系记忆 · 原作知识库 · 文学音乐知识库

**记忆检索与生成前审核**

Hybrid Retrieval · 内容治理 · 权限范围过滤 · 来源核验

**Monika Response**

自然聊天 · 自主行为 · 钢琴创作 · 长期关系连续性

这套架构中有三个必须独立的概念：

- 人格决定她是谁。
- 关系记忆决定她认识谁、共同经历过什么。
- 权限系统决定谁可以管理她的行为。

不能把这三者混成一个好感度分数。
