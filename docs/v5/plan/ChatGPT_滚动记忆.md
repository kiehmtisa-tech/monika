## 一、这次 60 秒超时究竟说明了什么？

OpenClaw 提供了几个关键数据：

| 指标 | 观测值 | 判断 |
|--------|--------|--------|
| Planner 输入 | 18.3k tokens | 对普通 QQ 私聊而言偏大 |
| 请求体 | 115 KB | 需要检查具体内容构成 |
| 上下文项目 | 106+ items | 不能简单等同于 106 条 QQ 消息 |

这说明问题不一定出在聊天记录太长，而可能出在每轮请求附带的系统提示、工具定义、工具调用历史、插件注入内容或记忆检索结果。

尤其值得注意的是：**如果这 18.3k tokens 主要来自每轮重新注入的工具定义和系统内容，那么无论开多少次新对话，下一轮仍然可能达到 18.3k。**

- System Prompt 和人格设定
- 最近 QQ 聊天历史
- 滚动上下文摘要
- A\_Memorix 人物画像及检索结果
- 工具定义（Tool Schemas）
- 工具执行结果与历史调用
- 主动插件或测试注入的内容

另外，18.3k tokens 并没有超过 MiMo Flash 常见的长上下文容量；**上下文容量足够，不代表推理延迟一定能满足 60 秒的客户端要求**。输入越长、工具决策越复杂，延迟越可能变得不稳定。

这里还要区分正常使用与注入测试：如果测试一次性塞进了大量工具结果，超时可能主要是测试负载造成的，不能直接认定大肥鱼日常聊天也会持续膨胀。

## 二、其他大肥鱼项目是怎么处理的？

我找到了三个与你的问题直接相关的实现思路。

### 1. MaiBot 官方：滚动摘要 + 长期记忆 + 工具结果压缩

MaiBot 从 **v1.3.15（2026 年 10 月 23 日）** 开始，已经将上下文压缩调整为“滚动状态摘要”。

当较早的聊天内容需要裁切时，系统用 Utils 模型生成一份摘要，后续 Planner 继续携带它，而不需要一直保留所有早期消息。

官方提供以下参数： [MaiBot 文档中心](https://docs.maibot.chat/changelog/?utm_source=chatgpt.com) [配置](https://docs.maibot.chat/manual/configuration/bot-config?utm_source=chatgpt.com)

```toml
[chat]
max_private_context_size = 75
context_compaction_summary_max_chars = 6000

[capabilities]
tool_result_condense = false
tool_result_condense_threshold = 3000
```

其中 `tool_result_condense` 特别适合调查你当前的故障。

开启后，超过设定长度的工具结果会先经过子代理压缩，再写入后续上下文，而不是直接塞入整份结果。代价是会增加一次模型整理请求，因此需要同时测量单轮延迟和成本。 [配置](https://docs.maibot.chat/manual/configuration/bot-config?utm_source=chatgpt.com)

这也意味着：**MaiBot 本身已有部分能力，不需要从零做一套完整的上下文压缩系统。**

### 2. DSH 大肥鱼：有限记忆注入，而不是无限携带历史

**[dsh-fish-memory（鱼的记忆）](https://github.com/Yuuyuko-uu/dsh-fish-memory)**

这是另一个大肥鱼生态的记忆插件，思路很值得借鉴，但不能直接安装到 MaiBot。

它的记忆设计有几个特点：

- 不记录全部聊天，只挑选有意义的信息。
- 默认每天最多新增 8 条记忆。
- 每次按相关性选取少量记忆，默认最多注入 6 条。
- 注入内容总量默认限制在约 800 字。
- 重要事实可以长期保留，普通记忆随时间降低被检索到的概率。

这些行为和具体默认值来自该项目的 README。 [GitHub](https://github.com/Yuuyuko-uu/dsh-fish-memory?utm_source=chatgpt.com)

对你的 A\_Memorix，我最想借鉴的不是它的记忆数据库，而是 **限制每轮注入量**。

A\_Memorix 可以存储大量记忆，但每轮 Planner 只应该得到当前对话真正相关的少数几条。更多细节可以在需要时主动检索。

### 3. 社区 MaiBot 优化插件：主动裁剪 Planner 上下文

**[Maibot Group Chat Logic Optimizer](https://github.com/Luoyehe/Maibot-group-chat-logic-optimizer)**

社区的群聊逻辑优化插件，在 README 中明确提到对聊天上下文进行裁剪，并提供 `context.max_history_messages` 参数，默认保留 30 条。

它不仅关注历史长度，还处理 Planner/Replyer 规则、工具调用后的等待和重复回复等问题。 [GitHub](https://github.com/Luoyehe/Maibot-group-chat-logic-optimizer/blob/master/README.md?utm_source=chatgpt.com)

不过，它主要面向群聊，README 的兼容说明涉及 MaiBot 1.2.x，不能直接假定适用于你当前的 1.3.x Docker 版本，也不能假定它会解决工具定义过大的问题。

### 三种方案的共同点

| 项目 | 核心做法 | 值得借鉴的部分 |
|--------|--------|--------|
| MaiBot 官方 | 滚动摘要、工具结果压缩 | 优先使用原生功能 |
| dsh-fish-memory | 选择性记忆、限制注入量 | 长期记忆与短期上下文分离 |
| 社区群聊优化器 | 裁剪历史、精简交互流程 | 每轮输入设置明确上限 |

我没有在这些项目中确认到一种可以直接用于你当前 QQ MaiBot 的、完整验证过的“达到阈值自动开新会话但保留 A\_Memorix”现成方案。更稳妥的是先复用官方压缩能力，再针对你的部署实现一个安全的会话轮换机制。

## 三、我建议你采用「上下文生命周期管理」

这比单独调整 `max_private_context_size` 更符合你希望长期养成大肥鱼的目标。

**QQ 消息 / 主动发言事件**

同一个 QQ 聊天流持续存在

**Planner 上下文管理器**

工具筛选 · 结果压缩 · 最近消息 · Token 预算

**短期会话**

当前话题、最近消息、必要的工具结果

**A\_Memorix**

人物画像、共同经历、稳定偏好、长期事实

**MiMo Planner → DeepSeek Replyer**

只获取本轮真正需要的内容

**上下文超限 → 压缩或重置短期会话**

保留长期记忆与 QQ 聊天身份，不必重新认识群友

我建议分成三个处理等级。

| 状态 | 建议初始触发条件 | 自动处理 |
|--------|--------|--------|
| 正常 | Planner 输入不超过 8k tokens | 不处理 |
| 压缩 | 8k～12k tokens | 裁剪历史工具结果，压缩旧对话 |
| 重置候选 | 超过 12k tokens，且压缩后仍超限 | 安全轮换短期会话，保留长期记忆 |

这些只是第一版的实验阈值，最终要根据 MiMo 的实际首 Token 延迟、完整响应耗时和你的网关统计调整，并不是 MaiBot 官方推荐值。

**但有一项必须强调：重置短期会话不能解决工具定义本身过大的问题。** 如果一轮新会话的基础 Prompt 就超过 12k，应该首先精简基础 Prompt，而不是反复重置。

### 建议先做的优化

我建议采用下面这组起点。

| 部分 | 初始优化建议 |
|--------|--------|
| 最近私聊消息 | 20～40 条，保留近期有效对话 |
| 滚动摘要 | 将最大长度从 6000 字符测试性降低至 2000 字符 |
| 自动画像注入 | 优先当前聊天对象，先测试 1～2 份 |
| 记忆主动检索 | 每次默认 3～5 条，控制输出总长度 |
| 工具结果 | 大结果转为简短摘要或引用，必要时按需读取 |
| 工具定义 | 仅暴露当前聊天模式需要的工具 |
| 历史工具调用 | 只保留当前未完成任务必需的调用链 |

工具结果压缩可以先测试 MaiBot 原生 `tool_result_condense`，但如果它使当前轮处理更慢，就应该考虑确定性裁剪和按需检索，而不是给每个工具结果增加一次 LLM 调用。

同样，我不建议简单把 Planner 超时时间从 60 秒改为 120 秒。这样可能掩盖真正的输入膨胀，还会让大肥鱼回复很慢。

## 四、清空会话时，哪些必须保留？

这里最重要的是：**QQ 的聊天流 ID、短期 Planner 会话与 A\_Memorix 的长期记忆，不应该被当成同一种数据。**

| 数据 | 安全轮换时 |
|--------|--------|
| QQ 用户 ID、聊天流 ID | 保留 |
| 人格初始设定 | 保留 |
| A\_Memorix 人物画像 | 保留 |
| 长期事实、Episode、记忆索引 | 保留 |
| 原始 QQ 消息数据库 | 保留 |
| 最近必要的聊天上下文 | 少量保留 |
| 旧的滚动摘要 | 重新生成简短交接摘要 |
| 已完成的工具调用结果 | 清理出活跃上下文 |
| 尚未完成的工具任务 | 等待完成或安全中止 |

这样你可以在 QQ 中继续使用同一个聊天窗口，只是后台 Planner 开始一轮新的短期会话。

正常情况下，大肥鱼仍然认识你，因为过去的共同经历在 A\_Memorix 中，可以通过当前人物身份和记忆检索重新获得。

但是需要 OpenClaw 验证当前 MaiBot 是否提供了能够安全清理指定聊天流运行时上下文的接口。**不要直接删除聊天数据库记录，也不要简单修改 `stream_id` 来伪造新会话。**

## 六、最终建议

对于你现在的系统，我认为最合适的长期架构就是：

**A\_Memorix 保存长期记忆 + MaiBot 原生滚动摘要 + 动态工具筛选 + 超限时安全轮换短期会话。**
